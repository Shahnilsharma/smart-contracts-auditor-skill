# Anchor / Solana program coding standards

- **Signer checks**: every instruction that requires authorization uses `Signer<'info>` in the accounts struct for the authorizing party — never just compare a `Pubkey` field without also requiring it be a transaction signer.
- **Owner checks**: use `Account<'info, T>` (Anchor deserializes and checks the account is owned by *this* program and matches the expected discriminator) rather than `AccountInfo<'info>` for any account whose data you trust — `AccountInfo` skips all of that and is a common source of "missing owner check" bugs when used carelessly.
- **PDA derivation**: always derive with `seeds = [...], bump` constraints and let Anchor store/validate the canonical bump; never accept a bump as raw instruction input and never reuse the same PDA seed scheme across different authority domains/roles (PDA sharing across roles is a real, common vulnerability).
- **Arithmetic**: `checked_add`/`checked_sub`/`checked_mul`/`checked_div` (or `saturating_*` where saturation is the intended semantic, documented as such) on every value amount — Rust release builds (which Solana programs are) do not panic on overflow by default, so an unchecked operation silently wraps.
- **CPI**: type the target as `Program<'info, KnownProgram>` (Anchor) so the program ID is checked automatically; in native code, explicitly compare the invoked program's key against the expected constant. Never CPI into a program ID taken unchecked from instruction data or a user-supplied account.
- **Account closing**: use Anchor's `#[account(mut, close = destination)]` constraint — it zeroes the account data and transfers all lamports atomically in a way the runtime treats as fully closed, rather than a hand-written lamport transfer that can leave the account revivable within the same transaction.
- **Re-initialization**: use Anchor's `init` constraint (which itself guards against re-running on an already-initialized account) rather than a manual "if not initialized" check that can race or be bypassed.
- **Sysvars**: access via Anchor's typed `Sysvar<'info, Clock>` etc. (validates the sysvar account address automatically) rather than reading an `AccountInfo` and trusting its address is correct.
- **Token handling**: prefer the `anchor-spl` typed wrappers (`TokenAccount`, `Mint`, `token::transfer`/`transfer_checked`) over raw CPI construction; use `transfer_checked` (validates mint + decimals) over plain `transfer` where available/required by the token program in use (mandatory for Token-2022).
- **Compute budget**: be mindful of CU-heavy operations (loops over accounts, complex math, many CPIs) — profile with Mollusk's compute-unit reporting or `solana program show`-style tooling; request additional compute budget via `ComputeBudgetInstruction` only when genuinely needed, don't paper over an inefficient instruction.
- **Errors**: define a custom `#[error_code] enum` with descriptive variants (Anchor convention) rather than generic panics/unwraps — no `.unwrap()`/`.expect()` reachable from instruction handlers on user-influenced data.
- **Upgrade authority**: document who/what holds it (single key, multisig, or `None`/immutable) as part of the architecture doc, not an afterthought at deploy time.
