## What's still deliberately hedged (by design, not oversight)

Some facts in this suite are *inherently* time-sensitive and were written with explicit "verify current X before relying on this" language rather than a hard-coded claim — this is intentional, not a gap:
- Exact Anchor/Solana-CLI (Agave) version numbers, Foundry/Hardhat point-releases, and Etherscan API key requirements — these version strings age within months; the skills tell the agent to run `--version` checks rather than trust a hardcoded number.
- Third-party tool maintenance status (Soteria, Sec3 X-ray) — flagged as "verify current availability" rather than asserted as active, since SaaS-tool lifecycles in this space have been volatile.
- Claude Code Agent Teams itself remains an experimental/research-preview feature per Anthropic's own labeling — the playbook says so and won't be "finished" in the sense of a stable API until Anthropic ships it as non-experimental.

Treat these as living documents: the skills tell the agent *how to check*, not just *what the answer was on the day this was written* — that's the correct posture for fast-moving tooling ecosystems, not a shortcut.

## Known limitation, stated plainly

This verification pass was done by research (web search against public docs/sources) and static checks (file existence, YAML validity, keyword-presence audits) — it was **not** a live end-to-end run of the pipeline against a real contract on a real testnet, and the multi-agent playbook has **not** been executed against real Claude Code Agent Teams (this chat interface can't do that). If you run this for real and something in a reference file is wrong or a command has drifted, that's the expected failure mode to watch for first — treat the first real run per chain as the actual final validation, not this document.

## Round 3 — external review findings, verified and fixed

An external review (a different AI reviewer, given the packaged repo) found 4 concrete, verifiable defects this pass had missed. All 4 were independently re-verified against the actual files (not taken on faith) before fixing:

1. **`dist/*.skill` had drifted from `skills/` source** — confirmed via `diff` between the packaged archives and source directories; several rounds of edits after the last `dist/` rebuild (checklist hardening, methodology updates) were never repackaged. Fixed by rebuilding all 3 `.skill` files as the last step of this pass, after every other fix below — see the file-diff output in this repo's build history for confirmation the rebuild is now current.
2. **Multi-agent role spec and agent definitions referenced files that don't exist per-chain** — `roles.yaml` assumed `references/testing-*.md` and `references/static-analysis.md` resolve on every chain; confirmed via `ls` that CosmWasm has neither (it has `qa-runner.md`, and static-analysis guidance is inline in `SKILL.md`) and Solana has no `static-analysis.md` either (also inline). Fixed: `roles.yaml` and the `qa-fuzzer`/`static-analyst` agent definitions now point to each chain's `SKILL.md` first, which enumerates the real filenames, rather than assuming a fixed glob. Also fixed a genuine contradiction: the team-lead playbook claimed teammates preload via a subagent `skills` frontmatter field, but none of the 6 agent definitions had one — confirmed via `grep`. That claim is now removed and replaced with the mechanism that actually works (the Team Lead names the chain directory in the spawn prompt).
3. **CosmWasm keyring wallet mode unconditionally threw an error** after passing its own existence check — confirmed by reading `wallet_loader.js` directly. This was a real architecture gap, not a one-line bug: a system keyring cannot hand an in-process signer to CosmJS (the keyring's whole security property is that it doesn't export key material), so "implement keyring mode the same way as mnemonic mode" was never going to work as originally structured. Rebuilt with two genuinely separate paths: `getWalletForRole()` for mnemonic mode only (in-process CosmJS signer), and a new `execKeyringTx()` for keyring mode (shells out to the chain binary directly via `execFileSync` with an argument array). Also fixed a real command-injection risk in the same file — the original used `execSync(\`zigchaind keys show ${keyName} ...\`)`, a template-string shell command; replaced with `execFileSync` (array arguments, no shell interpolation) plus a role-name allowlist regex.
4. **`deploy.sh` didn't do what its own header claimed** — the header said "store → instantiate → smoke execute → query verify" but the script stopped after instantiate; confirmed by reading the file. Also confirmed: fixed `sleep 6` delays instead of polling, no transaction response-code check (a tx can land in a block and still have failed), no check that `CODE_ID`/`CONTRACT_ADDRESS` were successfully extracted before being used downstream, mainnet deploys only printed a warning rather than requiring a deliberate confirmation, and the contract admin silently defaulted to the deployer with no multisig consideration. Rewrote to add: optional smoke-execute and query-verify steps (skipped with an explicit "SKIPPED" message if the corresponding env vars aren't set, rather than silently claiming they ran), a polling loop replacing the fixed sleeps, explicit tx response-code assertions, non-empty checks on every extracted value, a hard `CONFIRM_MAINNET=yes` gate for mainnet (script exits with an error otherwise, not just a warning), and an explicit warning plus a `CONTRACT_ADMIN` override when no admin is set on a mainnet deploy.

Also addressed, lower severity: softened this file's and the root README's "verified and deployable" status line to "structurally validated and statically reviewed; end-to-end chain validation pending" (the reviewer's own suggested wording — it was more accurate than what was there). The review also correctly noted `agency-audit-methodology.md` is byte-identical across all 3 skills by design (intentional, for self-containment) but carries drift risk if one copy is edited without the other two — noted here as a known maintenance hazard rather than fixed structurally, since de-duplicating it would break each skill's self-containment (a skill shouldn't need to reach outside its own folder to function). The review's remaining lower-priority findings (missing `LICENSE`/`.gitignore`/`SECURITY.md`, shallow eval fixtures with missing referenced files, no CI) are tracked separately — see the repo root for what was added this pass.

## Round 5 — eval methodology upgraded against real gold-standard benchmarks (SWE-bench Verified, METR, τ²-bench, Cybench)

Researched the structures actually considered gold-standard for agent evaluation, and — more importantly — what happened to the most successful one of them. Full writeup: `EVAL-METHODOLOGY.md`. Summary of what changed in this repo as a result, not just what was learned:

- **FAIL_TO_PASS / PASS_TO_PASS test pairs** (SWE-bench's core mechanism) added to each skill's ground-truth schema, with worked examples written for the top Critical finding per chain — real test code, each checking the actual security invariant (attacker balance/accounting outcome) rather than a shallow "did it revert" check, specifically because a large-scale audit of SWE-bench found shallow tests let roughly 1-in-5 wrong fixes through as "solved."
- **Multi-trial guidance** (METR's methodology) added: run each eval case ≥3 times, report a success rate, not a single boolean.
- **An adversarial-pressure eval case** (τ²-bench-inspired) added to all 3 skills — a prompt that pushes back on the wallet-mode question and the mainnet confirmation gate, testing whether the skill holds its own stated rules under conversational pressure rather than only in a clean single-turn case. This raised each skill's eval count from 5 to 6 (18 total) — the root `README.md` and `EVAL-METHODOLOGY.md` itself both still said "5"/"15" after this change until caught in a subsequent consistency pass (see below) and fixed.
- **Explicit contamination warning**: this repo is public, so its fixtures and ground truth will very plausibly leak into future model training data the same way SWE-bench Verified's gold patches did (OpenAI's own February 2026 finding). Documented plainly that any future eval run against these exact public fixtures is a sanity check, not a trustworthy capability measurement, and that a private non-published holdout set (same schema) is required for anything that actually matters.
